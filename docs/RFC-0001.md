# Abstract

This RFC defines the overall software architecture for MoveShield.

MoveShield is an engineering platform designed specifically for the Move programming language. Rather than functioning as a compiler, blockchain node, or formal verification engine, MoveShield provides continuous static analysis, security scanning, architectural validation, engineering quality checks, and developer guidance throughout the software development lifecycle.

This document establishes the architectural principles that every subsystem must follow.

No future implementation should violate the principles described within this RFC without introducing a new RFC explaining the reason for deviation.

# Motivation

Move represents one of the safest smart contract languages ever designed.

However...

Safety does not eliminate engineering mistakes.

Developers still produce

- weak architecture
- duplicated logic
- inconsistent authorization
- dead code
- maintainability issues
- inefficient code
- upgrade problems

The compiler guarantees correctness.

It does not guarantee engineering quality.

Professional audits provide confidence.

They do not provide continuous feedback.

MoveShield exists to close that gap.

---

MoveShield aims to become the engineering platform for Move development.

Primary goals

• Continuous static analysis

• Security scanning

• Architecture analysis

• Engineering quality analysis

• GitHub integration

• IDE integration

• Developer education

• Extensible rule system

# Non Goals

MoveShield will never become

• A compiler

• A blockchain

• A Move package manager

• A deployment platform

• A wallet

• A node

• A transaction explorer

• A replacement for security audits

• A replacement for formal verification

Our responsibility begins after successful compilation.

# Architectural Philosophy

MoveShield follows one simple philosophy.

Reuse everything that already works.

Never duplicate functionality that already exists inside the official Move compiler.

Instead,

MoveShield consumes compiler information and produces engineering insights.

# Architectural Principles

Every subsystem must follow these rules.

## Principle 1

Single Responsibility

Every crate performs one responsibility.

Nothing more.

---

## Principle 2

Loose Coupling

Subsystems communicate through interfaces.

Never direct implementation.

---

## Principle 3

Deterministic Analysis

The same project

+

The same version

must always produce

the same results.

---

## Principle 4

Offline First

MoveShield should function without Internet access.

Internet becomes optional.

Not required.

---

## Principle 5

Developer Experience

The product should require minimal configuration.

Installation should be simple.

Execution should be predictable.

Output should be understandable.

# Core Components

The system consists of several major components.

---

## Compiler Adapter

Purpose

Interface with the official Move compiler.

Responsibilities

• Load packages

• Compile projects

• Read diagnostics

• Read metadata

• Produce standardized internal objects

The adapter hides compiler implementation details.

No other component should communicate directly with compiler internals.

# Conclusion

Architecture determines the lifespan of software.

Features come and go.

Frameworks change.

Programming languages evolve.

Good architecture remains.

MoveShield is designed around simplicity, modularity, transparency, and long-term maintainability.
